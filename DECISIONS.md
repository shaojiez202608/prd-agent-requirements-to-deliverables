# Decisions

When several options were possible, the more conservative one was chosen. Each entry gives the reason.

| ID | Decision | Alternatives | Reason |
|---|---|---|---|
| D-01 | The form never calls an AI service; copying is manual | Built-in API call | Non-goal in the requirements input. Keeps data out of automatic third-party calls and works offline |
| D-02 | Field definitions live in one `intake/schema.json`; the forms are built from it | Two hand-written HTML files | One source for required flags, options and examples, so they can be checked by a program |
| D-03 | Pending-item logic and the prompt compiler exist in JS (browser) and Python (CLI), with a byte-parity test | Python only (needs a server) or JS only (tests need Node) | Offline single-file forms need JS; tests and CI need Python. The parity test prevents drift |
| D-04 | Frontline form omits ID, identifier, data type, ranges, architecture and offline behaviour, so its prompt is always CLARIFY_ONLY | Let frontline users guess IDs | FR-8: do not fill by guessing. The PM supplies technical values |
| D-05 | Multi-select values are emitted in schema order; whitespace is collapsed | Keep click order | Same answers must give the same text regardless of click order |
| D-06 | thing-model.json is the reference for the check; a hint is added when all files disagree with it | Majority vote | FR-6 names the thing model ID as the primary key. Majority vote could make a wrong copy the reference |
| D-07 | Each deliverable carries ID, identifier and access in one fixed machine-readable place | Parse free text | Exact and testable. Free-text parsing would give false results |
| D-08 | A local deterministic generator fills the knowledge-base templates and acts as the agent's mock | Committed hand-written example only | Satisfies the mock-mode requirement. The example can be regenerated, and a test catches drift between templates and example |
| D-09 | Deliverables are in English; forms are bilingual (zh/en); PDF uses built-in Latin-1 fonts | Bundle a CJK font | Avoids a font licence review and a large binary in the repository. Recorded as a limitation |
| D-10 | PDF freshness is checked through the source SHA-256 in the PDF Keywords field | Parse the PDF text | No PDF parser dependency, and the check is exact |
| D-11 | AWS part limited to an optional private S3 bucket (plus log bucket) for bundles; no compute, no endpoint | No AWS at all; an API with Lambda | Deployment is optional in the requirements input. A bundle store is the only real need (distribution); compute would be built for its own sake |
| D-12 | SSE-S3 on both buckets, no KMS key | Customer managed KMS key | The log destination must use SSE-S3. A KMS key would leave a pending-deletion key after teardown in the sandbox. SSE-KMS is listed in the hardening checklist |
| D-13 | No `autoDeleteObjects`; buckets are emptied by a script before destroy | CDK auto-delete custom resource | Auto-delete adds a Lambda function and an IAM role. The script is limited to the stack's own buckets and to stack names with the `--prefix` value (default `proto-prd-`, the sandbox prefix) |
| D-14 | Prior-art list names only organisation-owned repositories and official pages | Name personal community repositories | The repository must not contain personal identifiers. Their coverage is summarised without names |
| D-15 | Knowledge base is at `knowledge-base/` with ASCII names `00-project-rules` … `10-project-cases` | `docs/00-项目规则` … as in FR-3 | The requirements input allows adjusting the names. `docs/` already holds the repository documents. ASCII paths avoid encoding problems in tools and the numbering is kept |
| D-16 | Structured values (timer list) are `string` with max length; the encoding is an open item in the PRD | Invent a JSON timer format | Do not guess. See OPEN-QUESTIONS |
| D-17 | Device demo is plain C99 with a HAL seam and a host stub | Vendor SDK sample | No real module or SDK may be named. C99 compiles anywhere |
| D-18 | Bundles are immutable by name; publish refuses unless both checks pass | Overwrite | Prevents silent replacement of reviewed deliverables. On S3 this is enforced per object with a conditional write (D-28) |
| D-19 | Every commit uses one project identity (`shaojiez <shaojiez@example.invalid>`, a reserved `.invalid` domain); commits made with an AI assistant carry a `Co-Authored-By` trailer | Global git identity of whoever commits | One consistent, non-routable identity in the history; the trailer records AI assistance as the project convention requires |
| D-20 | Example values such as the active power upper bound (99999 W) and the report interval range are synthetic | Real ratings | The requirements input treats rated power as a placeholder; the PRD carries a note to take it from the hardware datasheet |
| D-21 | Command timeout and retry policy are not part of the intake and appear as an open item | Pick a timeout | Not in the intake; not guessed |
| D-22 | The only external links are official documentation pages (AWS, Kiro, cdk-nag, uv) and the prior-art repositories | No links | The fact-check rule requires an official link for each claim. No customer or personal page is linked |
| D-23 | cdk-nag pinned to 2.x (`>=2.30,<3`) | cdk-nag 3.x | 3.x replaces the suppression API with the CDK Validations mechanism (marked experimental in its README). 2.x is the documented, stable path for the AwsSolutions pack |
| D-24 | CDK feature flag `@aws-cdk/aws-s3:serverAccessLogsUseBucketPolicy` on | Legacy LogDeliveryWrite ACL | Keeps ACLs disabled (bucket owner enforced) on the log bucket |
| D-25 | Text that reaches the quick-start PDF must be Latin-1; violations are pending items (`invalid`) when `quick_start` is requested | Bundle a CJK font; let the PDF step fail | No font licence review, and the person filling the form learns about it before generation instead of a crash afterwards. Chinese text stays possible when no PDF is requested |
| D-26 | The FR-7 files (PRD.md, quick-start.md/.pdf, device-demo/dp_table.h) are always required unless `--intake` names a smaller deliverable set; PROGRESS.md can only add required files | Take the planned list from PROGRESS.md as the whole truth | PROGRESS.md is written by the agent, so it must not be able to waive the core check by omitting a file. The intake is what the requester asked for |
| D-27 | The agent instructions of the prompt (FR-9) live in `knowledge-base/00-project-rules/system-prompt.md`. Python reads the file at run time; `build-forms` embeds the parsed lines in the HTML forms, and `compiler.js` takes them as an argument | Keep the text in both compilers; fetch the file from the browser | One reviewed, versioned source. The forms must stay single-file and offline (no fetch), so the text is embedded at build time; `test_forms.py` fails if the embedded copy is stale |
| D-28 | S3 publish writes every object with `IfNoneMatch="*"` and the manifest last | `head_object` check before upload; S3 Object Lock | The condition is checked by S3 itself, needs only `s3:PutObject`, and has no race between check and write. A `head_object` probe would need `s3:ListBucket` to tell "missing" from "forbidden". Object Lock is listed as hardening |
| D-29 | `diff-model` treats any enum change except appending at the end as breaking, and rejects duplicate IDs | Compare enum values as a set; let the last duplicate win | Enum position can be the wire value; a silent merge of duplicates would hide a broken model |
| D-30 | Numbers in the prompt and deliverables are plain decimals (no exponent); integers beyond ±(2^53 − 1) are invalid | Keep each language's default `str()`/`String()`; arbitrary-precision decimals | Both languages print the same shortest round-trip digits; only the exponent notation differs, so expanding it is enough. JavaScript cannot hold larger integers exactly, so accepting them would make the two compilers disagree |
| D-31 | Visible IDs are checked only where they follow fixed patterns (see knowledge-base/09); other prose is not | Parse all prose; check nothing outside the markers | Fixed patterns are exact and cheap to test, and they cover every place the templates show an ID. Free-text parsing would give false results |
| D-32 | `<!--`, `-->` and `*/` are rejected in intake free text | Escape them per output format | They would create or close the dp-table markers, HTML comments or C comments. Rejecting is simpler than escaping for five output formats and is checked identically in JS and Python |
| D-33 | `deliverables.outputs` must include `thing_model`; `generate` exits 1 when its own validation fails | Generate without a reference; exit 0 and only write FAIL into PROGRESS.md | Without the thing model nothing can be checked. A failed validation must be visible to scripts, not only in a file |
| D-34 | `generate` writes into a temporary folder next to the target and moves the files into place only after every step succeeded | Write in place | A failure (for example in the PDF step) must not leave a partial deliverable set that looks finished |
| D-35 | The prompt header echoes `schema_version` and the form variant only when they are known values; marker neutralisation is case-insensitive | Echo the raw value (escaped) | The header is outside the data block, so any free text there would read as instructions |
| D-36 | LICENSE is MIT-0 with the line `Copyright Amazon.com, Inc. or its affiliates. All Rights Reserved.`; the git author stays `shaojiez <shaojiez@example.invalid>` | Placeholder copyright holder | aws-samples convention; the copyright line and the commit identity are separate questions |
| D-37 | Vulnerabilities are reported through the AWS vulnerability reporting page or aws-security@amazon.com, never in a public issue; SECURITY.md also documents resources, data handling, controls (mapped to files), caveats, hardening and cleanup | Platform-private reporting only | Standard AWS reporting path; one place for the security story of the prototype |
| D-38 | Placeholders: account ID `111122223333`, other values `<UPPER_SNAKE>`, host names `example.com`; CODEOWNERS uses `@<MAINTAINER_GITHUB_HANDLE>` until the maintainer is named (OPEN-QUESTIONS) | `<ACCOUNT_ID>` and free-form placeholders | Uniform, recognisable, and never mistaken for a real value; `tests/test_docs.py` rejects other 12-digit numbers |
| D-39 | Root `AGENTS.md` keeps the product's FR-3 reading order unchanged; contributor rules for AI assistants (role, commands, git flow, Always / Ask first / Never) are a separate last section "Contributing to this repository"; `CLAUDE.md` contains only `@AGENTS.md`; human contributor rules, including "explain every line an AI wrote", are in CONTRIBUTING.md | Move the reading order elsewhere; a second AGENTS.md in a subfolder | FR-3 requires the root file and Kiro reads it automatically; a subfolder AGENTS.md would also be loaded as steering (fact check row 3). A clearly scoped section keeps both uses in one file |
| D-40 | Config is committed only as `*.example.json`; real files are ignored and created by `make init`; validation (regex, ranges, cross-field rules, no 12-digit numbers) fails `cdk synth`; writer principal ARNs come only from `--context` | Committed real config; validation at deploy time | Keeps local edits and account-specific values out of git and fails before anything is deployed |
| D-41 | `make deploy` runs a read-only preflight with an explicit confirmation and refuses a `cdk diff` that deletes or replaces resources unless `ALLOW_DESTRUCTIVE=1`. No `ALLOW_PAID` switch: no command runs a paid evaluation or model call; the only cost is the deployed bucket, which `make deploy` itself creates after confirmation | Deploy without checks | Prevents deploying to the wrong account and accidental data loss on replacement |
| D-42 | The artifact bucket policy denies every principal outside the account (`aws:PrincipalAccount`) and, if configured, `s3:PutObject` by principals not in `writer_principal_arns`; the log bucket gets no principal-account deny | IAM only; the same deny on the log bucket | Resource policy as a second layer for the sensitive bucket; a principal-account deny on the log bucket could block delivery by the logging service principal |
| D-43 | One `scripts/ops.py` (preflight, diff guard, verify, cleanup, residue check, asset keys) replaces `empty_stack_buckets.py` and `residue_check.sh`; all output is masked (12-digit numbers replaced, account shown as last four digits) | Separate shell scripts | Testable with botocore Stubber, consistent masking and exit codes |
| D-44 | CI installs the gitleaks release binary after checking its SHA-256, instead of the gitleaks GitHub Action; the canary is a generated fake key scanned in a temporary folder (`gitleaks dir`) | gitleaks-action; a committed canary | The action needs a licence key for organisation accounts; a generated canary keeps credential-shaped strings out of the repository, and local commit hooks may block committing one |
| D-45 | CDK CLI pinned to `aws-cdk@2.1146.0` in the Makefile | `aws-cdk@2` | Reproducible synth and asset hashes |
| D-46 | Commit subjects were rewritten once to Conventional Commits before the standards pass; from then on history is not rewritten and v0.1.0 is tagged | Keep the old subjects | Verification records refer to commit hashes, which must stay valid |
| D-47 | Cleanup deletes only those CDK bootstrap bucket objects whose keys appear in this project's `cdk.out/*.assets.json`; earlier deployments are covered by synthesizing their commits | Leave all assets; delete by name pattern | The bootstrap bucket is shared; asset keys are content hashes and identify this project's objects exactly |
| D-48 | Local security scanning is recorded as incomplete where a scanner needs Docker or a large local install; those scanners are left to CI on GitHub | Install every scanner locally | The maintainer's machine has no Docker and should not collect tools; the gap is stated in VERIFICATION.md instead of hidden |
